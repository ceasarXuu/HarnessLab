## 1. 走查目标

v1.0.5 计划内阶段（Stage 0-12）均已 Done。本轮走查以真实用户视角在本地 API 模式
（前端 http://127.0.0.1:5173/，后端 http://127.0.0.1:8765/）下验收产品体验，收集并记录
问题、推动闭环，最终形成第一轮走查结论。

## 2. 范围与判定口径

- 覆盖页面：Jobs、Datasets、Agents、Environments、Leaderboard、System，以及 New Job、
  Job 详情等操作链路。
- 运行模式：API 模式（真实 `/api/webui/v1` 契约），不使用 mock。
- 问题严重度分级：

| 级别 | 定义 | 处理要求 |
|---|---|---|
| P0 | 阻断发布或数据安全风险 | 立即修复并回归 |
| P1 | 功能错误或主流程不可用 | 本轮走查内修复 |
| P2 | 体验/交互问题，功能可用 | 记录并安排修复 |
| P3 | 建议优化项 | 记录，择期处理 |

- 状态机：`open`（已记录）→ `triaged`（已评估）→ `fixing`（修复中）→ `closed`（已闭环）。
- 结论：`accepted`（确认为问题）、`won't-fix`（不修，需说明理由）、`by-design`（符合设计）。

## 3. 流程

1. 用户反馈问题 → 记录到[走查问题台账](issues.md)。
2. 复现并判定严重度与结论。
3. 需要修复的进入修复，并执行对应前后端门禁回归。
4. 走查收尾生成第一轮走查结论。

## 5. 记录模板

新增问题按以下字段追加到 `issues.md`：

```text
### W1-<NN> <短标题>
- 日期：YYYY-MM-DD
- 模块/页面：<页面或功能>
- 严重度：P0/P1/P2/P3
- 现象：<用户看到的实际行为>
- 复现步骤：1. ... 2. ...
- 期望行为：<预期结果>
- 实际行为：<观察到的结果>
- 结论：open / triaged / fixing / closed（accepted / won't-fix / by-design）
- 备注：<日志、截图或相关代码/文件引用>
```
